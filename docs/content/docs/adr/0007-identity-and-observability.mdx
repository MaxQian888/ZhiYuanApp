# 0007 · 身份、限流与可观测性

**状态：** 已接受 · **日期：** 2026-08-22

## 背景

控制台可以起飞、降落和急停真实无人机。在此之前，取得这套能力所需要的全部东西就是一个用户名和一个密码，而密码可以被无限次猜测。

同时，运维侧缺三样东西：出问题时无法把一条报错和日志里的某几行对应起来；无法回答"平台现在是不是健康的"；以及最要命的一条 —— 一套忘记设置环境变量的部署会带着仓库里那个 JWT 密钥正常启动。

## 决策

### TOTP 二次验证

RFC 6238，SHA-1 / 6 位 / 30 秒步长 —— 这三个参数不做配置项，因为任何偏离都会产生"验证器显示的码就是不对"这种无法从手机侧排查的故障。

算法**自己实现而不是引入依赖**：八十行、有 RFC 公布的测试向量，因此这个文件的正确性是测试套件能够真正证明的，这比引入一个之后需要长期跟踪 CVE 的库更划算。

**注册分两步。** `/auth/mfa/setup` 生成并存储密钥但不启用；只有 `/auth/mfa/confirm` 用一个有效验证码换来启用与恢复码。扫完码却在确认前弄丢手机的人，损失的是几分钟，不是账号。

**一个验证码只能用一次。** `admins.mfa_last_step` 记录已接受的时间步，推进用带条件的 `UPDATE ... WHERE mfa_last_step < ?`，两个实例并发处理同一个码时只有一个会命中。代价是：刚确认注册就立刻重新登录的人，需要等下一个验证码 —— 这是正确的 TOTP 行为，界面上会明确说"该验证码已被使用"。

**恢复码**十个，BCrypt 存储，一次性，字母表剔除了 O/0/I/1/L —— 这些码会在事故中被人念给另一个人听。用过的行保留不删：「已被使用」和「从来不存在」是两个不同的答案，事故中这个区别告诉你是否有别人先到了。

### 登录限流

同一 (username, IP) 十五分钟内五次失败即锁定，**记在数据库而不是进程内存**。多实例部署下，内存计数器给攻击者的实际额度是"五乘以当前实例数"，而实例数会随扩容变化 —— 那等于没有一个能说得出口的限制。

键必须是这个二元组：只按用户名会让一个攻击者在事故中把所有操作员锁在控制台外面，那是套着安全控制外衣的拒绝服务；只按 IP 会让一间办公室共用一份额度。

锁定期按**最早那次失败**过期，因此解锁是一次还一次，而不是一次还五次。响应带 `Retry-After`，把死路变成一句可执行的指示。

**验证码失败与密码失败共用同一份额度。** 六位数只有 10^6 种可能，已经拿到密码的攻击者否则可以从容爆破第二因子。

### 生产配置 fail-fast

**任何不是 `development`/`dev`/`test` 的 profile 都按生产处理。** 这个方向是反过来的，故意的：忘记设置 profile 会得到一次拒绝启动 + 一张待修列表，而不是一套用着仓库里那个密钥的部署。

检查在 `ApplicationPreparedEvent` 上执行 —— 环境已完全解析，但还没有任何 bean 被创建，因此它在数据源连接、Flyway 迁移和端口绑定之前就跑完了。等到应用已经在服务流量才报警的守卫，已经失职了。

**一次报出全部问题**，而不是第一个。一次一个会把五分钟的修复拖成五个部署周期。

### Trace ID

每个请求一个 ID：入站的 W3C `traceparent` 优先，其次 `X-Trace-Id`，都没有就生成。写进 MDC（结构化日志编码器会把它作为字段输出）、写进 `X-Trace-Id` 响应头、写进 `ApiResponse.traceId`。

操作员从报错上读到的那串字符，必须就是日志里能搜到的那一串，否则"请把 trace ID 发我"只是走过场。此前每个响应生成一个新 UUID，看起来一模一样，但毫无用处。

客户端提供的 ID 经过**校验而不是信任**：它会被回显进响应头和每一行日志，含换行的值等于让客户端自己写日志。

### 健康检查分级

**没有任何子系统会报 DOWN。** 只读性质的 `DEGRADED` 状态映射到 HTTP 200，并且不进 readiness 组。

因为 readiness 里的 DOWN 会把实例摘出负载均衡。这对"这个实例无法处理请求"是正确响应，对"MQTT broker 连不上"则完全相反 —— broker 挂掉时所有实例会同时失败，控制台跟着一起消失，而操作员失去的正是那块本可以告诉他们发生了什么的屏幕。

- `/actuator/health/liveness`、`/actuator/health/readiness` —— 公开，只返回状态。探针需要的是 UP 或 DOWN，不是我们的队列深度。
- `/actuator/health` —— 管理员，完整组件详情。
- `/actuator/**` 其余 —— 管理员。

指标用 **OTLP 推送**而非 Prometheus 抓取：多实例部署下，被替换掉的实例其指标不会因为死在两次抓取之间而丢失。所有 gauge 直接读平台已有的计数器，不另建一套 —— 两个本应相等的数字最终一定会不一致，然后两个都没人信。

## 考虑过的其他方案

**A. 短信验证码。** 拒绝：依赖运营商通道，SIM 劫持是已知攻击面，且事故中信号最差的时候恰恰最需要它。

**B. 内存限流（如 Bucket4j 本地模式）。** 拒绝：见上，多实例下额度不可陈述。分布式限流器（Redis）能解决，但为一张每天写入几十行的表引入第三个中间件不划算。

**C. 用 Spring profile `production` 触发配置检查。** 拒绝：失败模式是静默的 —— 忘记设 profile 就等于关掉检查。反向判定让"忘记"变成"启动失败"。

**D. 把 MQTT 连接状态放进 readiness。** 拒绝：见上，broker 故障会连带整个控制台下线。

## 后果

- 本地运行服务端必须带 `SPRING_PROFILES_ACTIVE=development`，否则守卫会拒绝启动。测试由 surefire 注入 `test`。
- 测试资源里**不能**再出现 `application.yml`：同名文件会遮蔽主配置，导致 management、logging、health 的所有设置从未被任何测试覆盖过。改用 `application-test.yml` 叠加。
- 二次验证的注册界面在设置页，密钥以分组文本 + `otpauth://` 链接呈现；**没有渲染二维码**，那需要引入一个 QR 库，目前手动输入已经可用。
- 恢复码只在确认注册与重新生成时各显示一次，之后无法再查看。
