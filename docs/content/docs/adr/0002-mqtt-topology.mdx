# 0002 · MQTT 设备链路拓扑

**状态：** 已接受 · **日期：** 2026-08-22 · **修订：** 2026-08-30（mTLS 强制与设备 ACL）

## 背景

现有 `SimulatorUavAdapter` 在进程内伪造设备行为，足以演示界面，但不构成设备链路。生产目标是 50–500 架无人机、飞行态 5Hz 遥测，即峰值约 2,500 msg/s，并且后端要多实例运行以满足 99.9% 可用性。

需要决定：协议版本、topic 结构、QoS、认证方式、多实例如何分摊消费。

## 决策

### 协议与客户端

MQTT 5，启用 **manual ACK**、自动重连，client ID 按实例唯一。

选 v5 而非 3.1.1 是为了拿到会话过期、原因码和用户属性 —— 用户属性让我们把 `traceId` 和 `commandId` 放进消息头而不是塞进 payload。

**修订（实现时）：** 原计划使用 Spring Integration 的 MQTT v5 adapter，实际改为**直接使用 Eclipse Paho MQTTv5 客户端**。

理由：我们对 broker 的全部需求就是 publish / subscribe / manual ack 三件事，Paho 用三个方法就能表达（`setManualAcks(true)`、`messageArrivedComplete(...)`、`subscribe(...)`）。Spring Integration 会额外引入 channel 与 message flow 这一整套概念，而我们不会使用其中任何一项 —— 多出来的抽象只会让"消息什么时候被确认"这个关键问题更难读。

代价是我们自己写 callback 与重连配置，约 60 行；这部分由 `UavAdapterContract` 覆盖，MQTT 子类在 CI 的 EMQX 容器上运行。

### 消息编解码

设备 wire format 由 `DeviceJson` **显式固定**，不继承应用的 Jackson 配置：`Instant` 一律 ISO-8601 UTC，未知字段忽略。

固件的发布节奏与平台不同，不能因为平台升级了一个库、改变了时间戳的写法就要求固件重新发版。忽略未知字段是为了前向兼容 —— 真正不兼容的变更由 `schemaVersion` 把关。

### Topic

```
zhiyuan/v1/uavs/{uavCode}/telemetry       设备 → 平台   QoS 1
zhiyuan/v1/uavs/{uavCode}/presence        设备 → 平台   QoS 1, retained, LWT
zhiyuan/v1/uavs/{uavCode}/command-acks    设备 → 平台   QoS 1
zhiyuan/v1/uavs/{uavCode}/commands        平台 → 设备   QoS 1
zhiyuan/v1/platform/events/{eventType}    平台 → 平台   QoS 1
```

`v1` 段是**协议版本**，与 API v1 独立演进。用 `uavCode` 而非数据库 `id` 分片：设备固件不应该知道我们的主键。

### QoS 与投递语义

全部 QoS 1（至少一次）。**不使用 QoS 2** —— 它的四次握手把吞吐砍掉一半，而幂等性我们本来就必须自己保证（设备重启、平台重放都会产生重复）。

去重靠消息里的 `eventId` + `sequence`，业务侧幂等。

### 消息信封

每条消息都带 `schemaVersion`、`eventId`、`uavCode`、`sequence`、`observedAt`。坐标 WGS-84，时间 UTC，`sequence` 设备侧单调递增。

字段缺失或 `schemaVersion` 不认识 → 计入 `mqtt.invalid.messages` 指标并 ACK 丢弃，**不重试** —— 格式错的消息重投一万次还是错的。

### 认证与授权

设备用 **mTLS**，证书 CN 即 `uavCode`。broker ACL 只允许每台设备读写自己那五个 topic。这样一台被攻破的设备无法监听或伪造其他设备。

生产平台连接同样必须使用 mTLS。`ProductionConfigGuard` 拒绝 `tcp://`，并要求以下四个配置全部存在：

- `MQTT_TLS_KEY_STORE` / `MQTT_TLS_KEY_STORE_PASSWORD`：平台客户端证书与私钥，PKCS#12 格式。
- `MQTT_TLS_TRUST_STORE` / `MQTT_TLS_TRUST_STORE_PASSWORD`：只信任自管 MQTT CA 的 PKCS#12 trust store。

broker 的 `peer_cert_as_username = cn` 将已经通过 CA 验证的证书 CN 映射为 username；ACL 再以 `zhiyuan/v1/uavs/${username}/...` 约束 topic。两者缺一不可：只做 CN 映射而不强制 `verify_peer` 会允许自签名证书冒充任意设备，只做 mTLS 而没有 ACL 则仍允许一台合法设备访问其他设备的数据。

仓库保留两个明确隔离的运行面：默认 `mqtt` 服务是只供本地开发的匿名明文 broker；`mqtt-secure` 位于 `security-contract` Compose profile，使用临时 CA、强制客户端证书并启用 deny-by-default ACL。可在本地运行：

```bash
scripts/generate-mqtt-test-certs.sh
docker compose --profile security-contract up -d --wait mqtt-secure
MQTT_MTLS_URL=ssl://localhost:8884 \
MQTT_MTLS_PLATFORM_KEY_STORE="$PWD/build/mqtt-certs/platform.p12" \
MQTT_MTLS_DEVICE_KEY_STORE="$PWD/build/mqtt-certs/uav-01.p12" \
MQTT_MTLS_TRUST_STORE="$PWD/build/mqtt-certs/truststore.p12" \
mvn -f server/pom.xml -Dtest=MqttMtlsAclContractTest test
```

测试证书有效期只有两天且生成在 gitignored 的 `build/` 下，绝不能用于部署。生产证书由组织 CA 签发和轮换；broker 仅信任这套私有 CA，不信任公共 Web PKI。

生产部署使用 `docker-compose.mqtt-pilot.yml` 作为最小模板。证书通过 `MQTT_BROKER_CA_CERT_FILE`、`MQTT_BROKER_CERT_FILE`、`MQTT_BROKER_KEY_FILE` 指向宿主机 secret 并只读挂载，不把私钥写进镜像或仓库。`MQTT_TOPIC_ROOT` 在生产固定为 `zhiyuan/v1`；启动保护器会拒绝其他值，契约测试也直接引用同一 Java 常量，因此代码与静态 ACL 漂移会在真实 broker 测试中失败。

### mTLS 滚动切换与回滚

安全 listener 必须添加到现有 broker/cluster，而不是启动一个不做 bridge 的独立 broker。模板中的 TCP 与 mTLS listener 属于同一 EMQX 节点，共享 session、subscription 和消息路由，形成明确的双栈窗口：

1. 使用组织 CA 签发 broker、平台和设备证书；让 `MQTT_DATA_VOLUME` 指向现有 broker 数据卷，在同一节点上加载本配置，并设置 `MQTT_LEGACY_LISTENER_ENABLED=true`。旧 listener 使用内置密码认证，账号由只读的 `MQTT_LEGACY_USERS_FILE` 引导，绝不允许匿名连接。
2. 新版本平台可先以 `MQTT_ALLOW_PLAINTEXT_MIGRATION=true` 和 legacy 凭证连接同一 broker；随后把 `MQTT_URL` 与四个 `MQTT_TLS_*` 配置切到 8883。再分批切设备；未迁移设备仍通过同一 broker 被平台看见。通过连接数、拒绝日志、presence 和 command ACK 验证每批。
3. 所有设备切换完成且观察期结束后，关闭 `MQTT_ALLOW_PLAINTEXT_MIGRATION`，再设置 `MQTT_LEGACY_LISTENER_ENABLED=false` 并移除 1883 的网络暴露。

在第 3 步前回滚时，停止本批切换，并以显式迁移开关将设备和平台指回同一 broker 的受认证旧 listener。第 3 步后若需回滚，必须按受控变更重新启用旧 listener，不能通过放宽 mTLS、恢复匿名访问或绕过 ACL 快速处理。迁移账号在切换完成后吊销；开关的启停、负责人和计划关闭时间必须进入变更记录。

### 多实例

原始设备流用 **共享订阅** `$share/zhiyuan-ingest/zhiyuan/v1/uavs/+/telemetry` 消费，每条消息只有一个实例处理。

处理流程：

```
收到消息
  └─ MySQL 事务：写当前快照 + 写 outbox
  └─ ClickHouse：批量写原始遥测
  └─ 两者都成功 → manual ACK
```

outbox 再发布规范化平台事件到 `zhiyuan/v1/platform/events/{eventType}`，这一条用**普通订阅**（不是共享），所有实例都收到，各自扇出给自己的 SSE 客户端。

Outbox publisher 以 30 秒数据库租约领取最多 500 条，网络广播在领取事务提交后进行。失败组按 1、2、4、8、16、32、60 秒持久化退避，之后保持 60 秒；记录不会自动删除或进入死信。只有整组广播成功且 `claim_token` 仍匹配时才确认：telemetry 和 command ACK 各自批量合并，presence 按设备逐条成组，其余事件逐条成组。

### Outbox 滚动发布

`V8__outbox_leases.sql` 是可向后兼容的加法迁移，但新旧 publisher 不能混跑。生产发布必须分两步：

1. 先应用迁移，以 `REALTIME_OUTBOX_PUBLISHER_ENABLED=false` 滚动替换所有实例；确认旧版本实例数为零。
2. 再统一把 `REALTIME_OUTBOX_PUBLISHER_ENABLED` 切为 `true`。若回滚应用版本，先关闭 publisher，再回滚实例；不回滚迁移。

最老 pending 超过 60 秒时 `/actuator/health` 的 outbox 组件为 `DEGRADED`，但 readiness 保持 `UP`，以便运维仍能访问控制台和诊断接口。

### 指令闸门

只有设备 presence 在线**且**遥测新鲜（飞行态 ≤2s，地面态 ≤5s）才允许下发。离线或过期直接拒绝，**不排队** —— 一条延迟五分钟才送达的"返航"指令比拒绝更危险。

指令带 `commandId`、`expiresAt`、幂等键；8 秒内没有最终 ACK 转 `TIMEOUT`。

## 考虑过的其他方案

**A. 直接用 WebSocket，不引入 MQTT。** 拒绝：需要自己实现重连、QoS、遗嘱消息、per-device ACL，等于重写一个 broker。

**B. 用 Kafka 做设备接入。** 拒绝：Kafka 客户端对嵌入式设备太重，且没有 LWT 这类连接语义。Kafka 适合做平台内部总线，但那正是 outbox + MQTT platform events 覆盖的场景，引入第三个中间件不划算。

**C. 每个实例都消费全量遥测（不用共享订阅）。** 拒绝：2,500 msg/s × N 实例的重复解析和重复写库，扩容反而变慢。

## 后果

- 需要一个支持 MQTT 5、共享订阅和 mTLS 的 broker（EMQX、HiveMQ、VerneMQ 均可）。CI 用容器化 broker 跑契约测试。
- 设备固件需要按上述信封改造。过渡期 simulator adapter 与 MQTT adapter 通过**同一套契约测试**，在 staging 对照运行，但**不双发真实指令**。
- 证书生命周期管理（签发、轮换、吊销）成为新的运维职责，见 Slice 4 的灾备演练清单。
