# 0003 · 遥测留存与存储分工

**状态：** 已接受 · **日期：** 2026-08-22 · **修订：** 2026-08-30（真实归档契约）

## 背景

500 架无人机、飞行态 5Hz，一天的原始遥测约 2 亿行（按 30% 时间在飞估算）。这个量级不能进 MySQL —— 不是写不进去，而是它会把交易库的 buffer pool、备份窗口和 PITR 恢复时间全部拖垮，而遥测历史恰恰是**最不需要事务保证**的数据。

同时运营台确实需要历史：回放一次配送轨迹、查一台设备过去一周的电量曲线、事故复盘。

## 决策

**按访问模式切分存储，而不是按数据种类：**

| 存储             | 内容                        | 保留       | 事实来源           |
| ---------------- | --------------------------- | ---------- | ------------------ |
| MySQL            | 设备**当前**快照、业务事件  | 随业务     | 交易的事实来源     |
| ClickHouse Cloud | 原始遥测 `telemetry_raw`    | **7 天**   | 遥测历史的事实来源 |
| ClickHouse Cloud | 1 分钟降采样 `telemetry_1m` | **365 天** | 长期趋势与指标     |

`uavs` 表只有一行代表"这台设备现在在哪"，被遥测流不断覆盖。它是**派生的、可重建的** —— 真正的序列在 ClickHouse。

写入使用 ClickHouse HTTP(S) 接口，以 `JSONEachRow` **批量**提交（200 条或 500ms 取先到者）。每条样本带稳定的 `eventId`；`telemetry_raw` 用 `ReplacingMergeTree` 按 `(uavCode, observedAt, eventId)` 收敛重放，raw 查询再使用 `FINAL` 获得即时去重结果，不依赖后台 merge 是否已经完成。

`telemetry_1m` 由 Materialized View 写入 `AggregatingMergeTree`。状态、电量和坐标使用 `argMaxState(value, (observedAt, sequence, eventId))`，查询使用对应的 `argMaxMerge`；因此旧批次晚到或重放不会把轨迹回退到较早位置。高度、速度使用 `maxState/maxMerge`。分钟表不保存精确 event ID 集或样本计数：在 365 天、2,500 samples/s 的规模下，精确去重集合会比 raw 留存更大；吞吐和丢弃量由归档指标记录。一次分钟窗口可能来自多个 insert part，因此查询仍按 `(uavCode, minute)` 聚合；否则 merge 尚未发生时 API 会为同一分钟返回多点。HTTP 参数通过 ClickHouse 的 `{name:Type}` 与 `param_name` 传递，不拼接设备编号。响应中任意一行无法解析时整次查询返回 503，不返回看似成功的残缺轨迹。

已有环境用 `clickhouse/migrations/002_event_time_rollup_up.sql` 蓝绿替换分钟表：暂停归档写入，保留并继续更新旧表作为回滚目标，从旧降采样保留超过 raw 留存期的历史，再用 `telemetry_raw FINAL` 重建最近 7 天。观察期内可用配套 `down` 脚本回滚；新环境直接应用 `schema.sql`，不得重复执行迁移。

查询入口是 `GET /api/v1/uavs/{id}/telemetry?from&to&resolution=raw|1m`，`resolution` 显式选择表，**不做自动降级** —— 让调用方知道自己拿的是哪种精度。超出保留期的时间范围返回明确错误而不是空数组。

### 降级行为

ClickHouse 不可用时：

- 遥测**采集不中断**（MySQL 快照 + outbox 仍在事务里成功）；
- 历史查询返回 503 与明确的降级说明；
- readiness **不因此变红**（见 ADR 0002 的实例职责划分），但触发告警。

这是刻意的：让历史查询的故障拖垮实时监控是错误的失败模式。

## 考虑过的其他方案

**A. 全部放 MySQL，加分区表 + 定期归档。** 拒绝：2 亿行/天的插入会与订单事务争抢同一个实例的资源，而分区维护、归档任务、备份体积都会成为长期运维负担。

**B. 用 TimescaleDB / InfluxDB。** 两者技术上都可行。选 ClickHouse Cloud 是因为它的托管形态省掉了我们自己做副本、备份和扩容，而团队已有 ClickHouse 使用经验。这是团队因素驱动的决策，不是技术优越性判断。

**C. 只保留降采样，不留 raw。** 拒绝：事故复盘需要秒级精度。7 天的 raw 覆盖了绝大多数复盘窗口，成本可接受。

## 后果

- 引入第二个数据存储和它的凭据、网络路径与故障模式。生产配置缺少 ClickHouse 参数时**启动失败**（见 Slice 4）。
- 需要季度性的恢复演练同时覆盖 MySQL PITR 与 ClickHouse Cloud 备份。
- 前端的轨迹回放要显式选择 `resolution`，UI 上必须让操作员看得出自己在看 raw 还是 1m。
