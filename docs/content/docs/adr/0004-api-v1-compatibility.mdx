# 0004 · API v1 兼容策略

**状态：** 已接受 · **日期：** 2026-08-22

## 背景

生产化要往 API 里加不少东西：库存预留字段、幂等键、MFA 挑战、ASR 会话、遥测历史查询。同时已经有两类客户端在跑（Web 与 Tauri 桌面），而桌面端**无法保证所有用户同时升级** —— 这正是 updater 存在的原因。

## 决策

**`/api/v1` 在本次生产化中不做任何破坏性修改。**

具体规则：

1. **只增字段，不改语义。** `reservedStock`、`onHandStock` 是新增字段；`stock` 继续表示可用库存（见 ADR 0001）。旧客户端读到的每个既有字段含义都不变。
2. **幂等键是可选请求头。** `POST /api/v1/orders` 与 UAV 指令接口接受 `Idempotency-Key`。**新客户端必须发送**，旧客户端不发也能工作（退化为非幂等，与今天行为一致）。重复请求返回**原来那次**的业务结果，不是冲突错误。
3. **MFA 走新增响应字段。** `POST /api/v1/auth/login` 增加 `mfaRequired` 与 `challengeToken`。未触发 MFA 时响应结构与今天**逐字节一致**，旧客户端无感。
4. **新能力用新端点，不重载旧端点。** `/auth/mfa/*`、`/asr/sessions`、`/uavs/{id}/telemetry` 都是新路径。
5. **MFA 强制启用有前置条件：** 只有当所有正式客户端都支持 challenge 流程后才打开 enforcement。在此之前 `mfaRequired` 可以返回，但不强制。

破坏性变更要等到 `/api/v2`，并且需要一条新的 ADR 说明双版本共存期。

### 数据库迁移同样遵守

所有迁移采用 **expand/contract**：先加列/加表（旧代码无害），再切换写路径，最后（在一个后续版本里）才清理。这样迁移可以在多实例滚动发布中执行，不需要停机窗口。

## 考虑过的其他方案

**A. 直接发 v2，一次做干净。** 拒绝：需要同时维护两套实现，而本次改动没有一处**必须**破坏兼容。为了整洁而付出双版本成本不划算。

**B. 把 `stock` 改成在手库存，新增 `availableStock`。** 语义上更"正确"，但会**静默改变**旧客户端读到的数字含义 —— 一个还没升级的桌面端会在库存页显示错误的可下单数量，而且不会报错。这是最危险的一类变更，拒绝。

**C. 强制所有客户端发幂等键（缺失即 400）。** 拒绝：等于破坏性变更，旧桌面端会直接不能下单。

## 后果

- `reserved_stock` 的引入必须保证 `stock` 语义不变，这约束了 ADR 0001 的列设计 —— 两条 ADR 是耦合的。
- 幂等键在过渡期是"尽力而为"：旧客户端的重复下单仍可能产生两个订单。这个残留风险被显式接受，并在 Slice 1 的验收里作为已知缺口记录。
- 需要一套契约测试锁住 v1 响应形状，防止后续改动意外破坏兼容。
